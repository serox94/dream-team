# Audyt RYBY / Dream Team — 28 września 2026

## Ustalenia i zakres

Sprawdzono historię i pliki repozytoriów `serox94/ryby2026` oraz `serox94/dream-team`, migracje, API, warstwę zgodności starego frontendu, konfigurację wdrażania i produkcyjne ekrany. Produkcja działa pod https://dream-team.sewerynski00.workers.dev/ z repozytorium `dream-team`. Nie tworzono nowej aplikacji ani projektu Sites.

Poprzednia wersja była statycznym frontendem z Supabase; obecna korzysta z Worker, D1 i statycznych plików. Węzły, rigi, ilustracje, szczegółowe francuskie strony wiedzy, checklisty i pola spotów znajdują się w istniejących repozytoriach. Zachowano je. Wydzielono oryginalne bogate treści francuskie do `public/data/lakes/plaine2/`; nie pisano ich na nowo.

## Architektura i wdrożenie

- `ryby2026` zachowuje starszy frontend i historię Supabase; `dream-team` zawiera wdrażaną aplikację. Nie trzeba zakładać kolejnego repozytorium na następny rok.
- `public/` to jedenaście ekranów oraz moduły współdzielone. `src/worker.js` obsługuje statyczne pliki, API i istniejącą bazę D1. Łowiska, wyjazdy, załogi, połowy, spoty, checklisty i dokumenty są odrębnymi rekordami; szczegółowe teksty Plaine pozostają w plikach treści przypiętych do profilu łowiska.
- `migrations/` i `src/ensure-schema.js` przeprowadzają addytywną aktualizację schematu D1 z wersji 16 do 17. `wrangler.jsonc` wskazuje ten sam Worker i tę samą bazę. GitHub Actions uruchamia testy i build; Cloudflare Workers Builds publikuje gałąź `main`.
- Pogodę pobiera Worker z Open-Meteo na podstawie współrzędnych wybranego łowiska. Przeglądarka korzysta z `/api/weather?tripId=…`; żądający nie wybiera arbitralnego adresu usługi ani GPS.

Odczyt produkcji przed zmianami: wyjazd `next-trip` zawierał 64 pozycje checklisty (12 spakowanych) oraz 2 połowy, łącznie 23 kg. Były również wyjazdy La Plaine 2026, Wygonin 2027 i Miłoszewskie 2027. Zachowano te rekordy, również wpisy wyglądające na testowe. Nie wykonywano próbnych zapisów na produkcji.

## Supabase i ochrona danych

Znaleziono poprzednie publiczne połączenie Supabase i historię importera do D1. Bezpośrednie próby odczytu starych tabel zwracały HTTP 502. To nie dowodzi, że baza jest pusta. Nie usuwano niczego z Supabase, nie uruchamiano ponownego importu i nie kopiowano danych w ciemno. W D1 istnieje mechanizm znacznika wcześniejszego importu `supabase_import_v2`; nowa aplikacja zachowuje go i uwzględnia w eksporcie.

Kontrola z 28.09: pełny eksport **produkcyjnej** D1 zawiera 4 wyjazdy, 3 łowiska, 2 uczestników, 103 pozycje checklist (64 Francja listopad, 22 Wygonin, 17 Miłoszewskie), 84 dokumenty, 2 połowy (Francja listopad) i 0 spotów. Archiwalny wyjazd francuski z czerwca ma 0 połowów, 0 spotów, 0 checklist i 0 dokumentów. Zachowany znacznik importu z 03.09.2026 mówi: źródło miało 64 pozycje checklisty, 0 spotów i 0 połowów; importer dopisał 0 rekordów każdej kategorii, ponieważ checklista już istniała w D1. Weryfikacja historycznego kodu importera potwierdza znaczenie tych pól. Nie mamy dowodu, że między 03.09 a wyłączeniem starego źródła dopisano tam nowe rekordy. Brak pewnego punktu odniesienia do porównania 64 pozycji wiersz po wierszu, brak dostępu do aktualnego starego źródła; nie twierdzimy, że późniejsze dane nie istniały.

Trzy połowy z datami czerwcowymi w starym `ryby2026/app.js` to stała `FALLBACK_CATCHES`, zwracana przez ekran przy braku połączenia albo błędzie odczytu. Znacznik importu pokazuje 0 połowów w rzeczywistym źródle 03.09; tych trzech wpisów zastępczych nie dopisujemy do produkcyjnej D1 jako autentycznych połowów.

Aktualny kod uruchamiany w przeglądarce ani Worker nie ma połączenia, SDK, zmiennej środowiskowej, klucza czy URL Supabase. Dawny adapter zgodności nazywa się obecnie `d1-api-compat.js` i komunikuje się wyłącznie z lokalnym API Workera. Interfejs i endpoint zdrowia nie odczytują już znacznika importu; surowy rekord `app_settings` pozostaje nienaruszony w D1 i kopii. Wszystkie zapisy ekranów przechodzą przez Workera i D1; prognoza jest jedynym odczytem z zewnętrznej usługi Open-Meteo. Sam stary projekt nie jest potrzebny do działania produkcji.

Migracja została sprawdzona na bazie ze starym schematem i istniejącymi rekordami: wszystkie wcześniejsze pola połowów, spotów, checklisty, uczestników, wyjazdów i dokumentów oraz znacznik importu pozostały niezmienione. Nowe kolumny i tabele są dodatkiem.

## Weryfikacja i produkcja

- 19 testów: API na rzeczywistym SQLite, migracja ze starej bazy, start wszystkich 11 ekranów, tworzenie uczestnika i wyjazdu 2029, CRUD checklisty/połowów/spotów, cofanie usunięcia, izolacja wyjazdów, PB, walidacja, zmiana czasu i błędy odczytu.
- Testy DOM wykonują rzeczywiste pliki frontendu i handler Worker. Pogoda przechodzi przez rzeczywisty endpoint Workera z kontrolowaną odpowiedzią dostawcy; osobny test sprawdza współrzędne z bazy, brak GPS i błąd dostawcy. JSDOM nie renderuje canvas; wygląd wykresu sprawdzono w przeglądarce.
- `npm run build`: składnia JS, linki i pliki lokalne, bundlowanie Chart.js oraz Worker dry run.
- Wszystkie migracje zastosowane również lokalnym narzędziem Wrangler.
- `wrangler dev` w środowisku audytu zgłaszał błąd systemowy `uv_interface_addresses`; użyto lokalnego adaptera SQLite z tym samym kodem API.
- Przeglądarka chmurowa blokuje adres localhost. Zdalna wersja testowa i następnie produkcja 1.1.1 uruchomiły się na istniejących danych: 64 pozycje checklisty (12 spakowanych), 2 połowy o wadze 23 kg, wszystkie cztery wyjazdy i szczegółowy regulamin Plaine.
- Produkcja pokazuje poprawne daty Francji w `Europe/Paris`, brak daty dla Wygonina, właściwą załogę, archiwum, formularze zarządzania, PB 18 kg i 13 kg oraz plan łowiska. Nie robiono zapisów testowych na produkcji. Pogoda po poprawce pokazuje 22,2°C dla Francji i 14,5°C dla Wygonina, bez błędu aplikacji w świeżym widoku konsoli.
- Obejrzałem desktop o szerokości 1363 px oraz widoki 390/360 px (dashboard, wyjazdy, checklistę, mapę i rozwijane menu). Podgląd w ramce odtwarza szerokość ekranu; nie zastępuje testu na fizycznym telefonie. Narzędzie przeglądarki pokazało błąd żądania pogody przed poprawką i efekt po poprawce, ale nie udostępniło pełnego waterfall statusów wszystkich żądań.
- Kontrole `validate` na GitHub i produkcyjny Workers Build zakończyły się powodzeniem dla poprawki pogody. Ostateczny raport i wzmocnienie testu nie zmieniają zachowania aplikacji.

## Pozostałe kwestie

- Produkcja jest publiczna, zgodnie z dotychczasowym ustawieniem właściciela. API nie ma uwierzytelniania; znajomość adresu pozwala na zapis. Sprawdzenie pochodzenia żądań ogranicza zapisy z obcych stron, ale nie zastępuje logowania. Decyzja o ochronie dostępu jest oddzielnym krokiem.
- Do pełnego potwierdzenia historycznych danych sprzed wyłączenia starego projektu potrzebny byłby jego jednorazowy eksport. Porównania wymagałyby wyłącznie: lista 64 pozycji checklisty wraz ze stanem spakowania, ewentualne połowy lub spoty dodane po 03.09 oraz ich przypisanie do dawnego wyjazdu. Nie ma przesłanek do ponownej migracji całego projektu.
- Przygotowano ochronę zapisów/eksportu kluczem Workera i osobną codzienną kopię D1 do R2. Aktywacja wymaga sekretu, konta Cloudflare i zasobnika; szczegóły oraz obecny stan opisano w [backupie i dostępie](BACKUP-AND-ACCESS.md).
- Prognoza dotyczy bieżących warunków na wybranym łowisku. Indeks warunków jest orientacyjny, nie przewiduje rzeczywistych brań.
- Zmiana łowiska dla istniejącego wyjazdu odbywa się przez dodanie wyjazdu; historia starego pozostaje przypisana do właściwej wody. Nie wymaga nowej strony.

## Poprawka mechanizmu wdrożenia

Po przejściu kontroli GitHub i udanym buildzie podglądowym Cloudflare build produkcyjny zakończył się błędem. Publiczna przeglądarka nie ma dostępu do szczegółowego logu Cloudflare. Lokalny Wrangler także nie ma sesji do zdalnej D1. Wersja 1.1.1 przenosi addytywną migrację do samego Workera przy pierwszym żądaniu API na bazie w wersji 16. Zapisuje również znacznik `d1_migrations`, aby późniejszy standardowy Wrangler nie powtarzał migracji. Przy równoległych żądaniach i częściowo uzupełnionym schemacie sprawdza istniejące kolumny.
